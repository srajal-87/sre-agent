# Decisions Log

A running record of decisions, surprises, and trade-offs encountered during the build. Updated daily (3–5 sentences per session). This is the raw material for interview stories and the ARCHITECTURE.md "Decisions & Trade-offs" section.

## Phase 0 — Foundation

### Day 1: Repo setup and architecture scaffolding

Set up the repo structure to reflect the multi-service architecture — separate directories for victim services, agent logic, injector, eval, and infra. Chose to keep all victim services in Python/FastAPI for stack homogeneity (polyglot would add complexity without resume signal for this project). Docker Compose is the root orchestration for local dev — each service gets its own Dockerfile, composed together with Prometheus.

Key early decision: the fault injector controls faults via admin endpoints on the victim services (e.g., `POST /admin/fault`) rather than via environment variables or Docker restarts — this keeps injection fast and scriptable without restarting containers. Ground truth is logged by the injector, not the services themselves, so the agent can't accidentally "cheat" by reading the injection log.

CLAUDE.md written with full project context, conventions, and phase tracking — this is the continuity mechanism across Claude Code sessions over the 30-day build.

## Phase 1 — Victim System + Fault Injector + Telemetry

### Days 3–7: Three victim services, injector, and telemetry

Built the three FastAPI victim services (api-gateway → data-service → downstream-dep) via strict TDD, then the fault-injector CLI, and brought the whole stack up under docker-compose with Prometheus scraping all three. Each service is self-contained (its own copy of the `logging.py`/`metrics.py`/`faults.py` skeleton) — the minor duplication buys simple Docker build contexts and independent deployability, which we judged worth it for three services. After building api-gateway with full micro-step TDD (7 cycles), we switched to a batched cadence for the other two services (skeleton in one test-backed cycle, then fault+endpoint, then packaging) since the skeleton was now reviewed boilerplate — kept TDD discipline without seven near-identical approval gates each.

Two design choices worth recording. (1) Fault behavior is modeled by observable outcome, not literal mechanism: the gateway `timeout` fault sleeps out its real httpx budget then raises `TimeoutException` (so `http_request_duration_seconds` genuinely spikes), while `bad_config` short-circuits to a deterministic 500 (no latency signal to reproduce). (2) `downstream-dep` needed a multi-fault `FaultState` (a `dict` of active faults) because it supports `latency` and `memory` independently, unlike the single-slot state in the other two services. The `_StdoutHandler` that resolves `sys.stdout` dynamically was an unplanned but necessary fix — a `StreamHandler` caches the stream at construction, which broke pytest's `capsys` capture across tests.

Surprise during end-to-end verification: injecting `latency` (2000 ms) on downstream-dep produced a **504 at the gateway**, not a slow 200 — the added latency exceeded the gateway's real 2 s upstream timeout budget, so the slowness cascaded into a timeout. This is realistic and desirable (it exercises the real timeout path, not just the injected one), and it's exactly the kind of multi-hop symptom the agent will later have to disentangle.

Known gap found in verification (logged as Phase 1 tech debt): api-gateway does **not** gracefully handle a 5xx from data-service — `call_upstream`'s `raise_for_status()` raises `httpx.HTTPStatusError`, which is uncaught, so the gateway returns a 500 via Starlette's error middleware. Because that path bypasses our custom metrics middleware, the gateway 500 is not recorded in `http_requests_total` and logs a stack trace instead of a structured error. Fix deferred to a small follow-up (catch upstream errors → 502 + structured log + metric).

## Phase 2 — Storage (Supabase) + API Shell (FastAPI)

### Day 8: Persistence substrate and the `agent-api` service

Built the substrate the agent will plug into, with deliberately **no agent logic**: a Supabase Postgres database with `incidents` and `investigations`, and a FastAPI `agent-api` exposing `POST /investigate` (records an alert, returns IDs) and `GET /investigations/{id}`. The point of sequencing it this way is that Phase 3 only has to *fill in* an `investigations` row rather than also invent the plumbing around it. `POST /investigate` writes the incident **and** a `status='pending'` investigation stub in one transaction, so an incident can never exist without a row to complete later.

Account and access decisions. The project lives in the **personal** Supabase org, not the company one — the MCP server available in-session is authenticated to Zenisth AI and can only see that org, so the personal project had to be created through the **Management API** (`api.supabase.com/v1`) with a PAT. That also became the migration mechanism: checked-in `.sql` files applied via `POST /v1/projects/{ref}/database/query`, no Alembic. Migrations are the source of truth for the schema and `api/tests/test_models.py` asserts the ORM's column sets match them exactly — a drift alarm in both directions, at the cost of editing two places per column.

The connection string was the one real trap. `db.<ref>.supabase.co:5432` is **IPv6-only** on the free tier and unreachable from Docker Desktop on Windows; the Management API's pooler endpoint helpfully returns the `:6543` *transaction* pooler, which would break asyncpg's prepared-statement cache unless you also set `statement_cache_size=0` and `NullPool`. We use the Supavisor **session** pooler on `:5432` instead — IPv4, and asyncpg works unmodified. This is now documented in `.env.example` so the trap isn't rediscovered.

Two smaller choices. Pydantic models use **camelCase field names** (`groupKey`, `commonLabels`, `startsAt`) matching the Alertmanager wire format directly, which avoids alias/`populate_by_name` config entirely — the cost is un-Pythonic attribute names inside the app. And endpoint tests override a `get_repository()` FastAPI dependency with an in-memory fake, so the whole unit suite runs with no database and no `pytest-asyncio` while `TestClient` still drives the async handlers; real coverage comes from one integration test that skips unless `DATABASE_URL` is set. RLS is enabled on both tables with **no policies** — the API connects as `postgres` and bypasses RLS, so this denies all anon-key/PostgREST access while keeping the security advisor clean.

## Phase 3 — Agent Core

### Day 9: Sub-phase 3.1 — the three read-only investigation tools

Built `query_metrics`, `query_logs`, and `query_deploy_history` before any reasoning loop, on the principle that **each tool must be individually exercisable against the live stack during a real injected fault before the agent ever calls one**. Two rules govern all three, and both are deliberate divergences from the `ValueError`/`RuntimeError` convention used elsewhere in the repo. First, **a tool never raises for an expected failure** — Prometheus down, socket missing, unknown metric name all return `ok=False` with a readable `error`, because the caller is an LLM: a raised exception kills the graph, an error observation lets the agent adapt. Second, **empty is not failure** — `ok=True` with zero rows is a first-class answer, since "no deploys in the window" excludes a code change and traffic going flat *is* the evidence under a timeout fault. The internals stay strict: the pure builders raise, and only the tool boundary converts to the `ok=False` envelope.

**The agent does not write PromQL — the tool builds it.** A `KNOWN_METRICS` catalogue describes the six metrics the stack actually exposes, and the input names a metric plus filters and an aggregation. With a metric surface this small and fully known, free-form PromQL would buy nothing but hallucinated metric names, empty results misread as "no problem", and non-reproducible eval runs; the built string still comes back in `query`, so citations quote real PromQL. A raw-PromQL escape hatch is a deferral, not an omission. Two validations exist purely to prevent a *dangerous success*: asking for a metric a service doesn't expose, or filtering on a label a metric doesn't carry, would otherwise return a perfectly valid empty result — which, under our own "empty is evidence" rule, reads as "no problem". Writing the tests also exposed that a single default aggregation cannot work: `rate` is meaningless for a gauge, so four of the six metrics would have failed on a default-constructed query. The default is now derived from the metric's type.

Backends and their traps. Logs have no queryable store — the services write JSON to stdout and nothing collects it — so `query_logs` reads container stdout through the Docker API, resolving containers by the `com.docker.compose.service` label rather than by name. That requires mounting `/var/run/docker.sock`, which is **root-equivalent host access**: acceptable for a local demo stack (and needed anyway by the Phase 6 `restart_service` tool) but it will not work on Fly.io, and it is the main security caveat of this phase. Deploy history had no source at all, so it is a synthetic ledger in **Postgres rather than a JSONL file**, because the Phase 5 eval must correlate deploys with `incidents.ground_truth_*` and a file would force a cross-source join — as a bonus the tool layer now spans three genuinely different backends (HTTP, Docker socket, SQL). Logs aggregate first and sample second: `level_counts` and `message_counts` are computed over the *full* match set while only the most recent `limit` lines are returned, which works unusually well here because the services log fixed message strings, making a top-10 histogram nearly diagnostic on its own.

Findings that changed the design. Rehearsing `bad_config` against the live stack produced captured proof of the Phase 1 tech debt: api-gateway logs **zero structured ERROR lines and zero 500s** during that fault — only raw tracebacks — because the uncaught `HTTPStatusError` bypasses both the metrics middleware and the structured logger. `unparsed_count` is therefore the gateway's *only* signal for that cascade, and two offline tests now pin that from real captured output. The deploy seeder's required property is that noise exists and that faults **sometimes** fire with no preceding deploy (p=0.7), or "a deploy exists" would trivially imply causation and the eval would measure nothing; ground truth records the absence as deliberately as the presence. Deploy messages must hint without naming the fault — the plan's own example, "tune connection pool timeouts", had to be reworded because `timeout` *is* a fault name and an agent could lexically match it while reasoning not at all. Two bugs came only from running things: a process-wide cached SQLAlchemy engine kept its asyncpg pool bound to the first event loop, so the second `asyncio.run()` died with "Event loop is closed" (the long-lived FastAPI loop hid it; the probe CLI and eval harness would not have been so lucky — the sessionmaker is now keyed per loop), and a summary claimed non-JSON lines were "also present" when they were in fact *part of* the reported match count. Smaller notes: metric statistics are computed **before** downsampling, so a two-scrape latency spike can't be sampled away into a healthy-looking `max`; `agent/logging.py` was dropped from the plan's file list because at package top level it shadows the stdlib `logging` module and breaks pytest outright; and `agent-api` now builds from a **root context** so the image carries both `api/` and `agent/`, which makes a root `.dockerignore` mandatory rather than optional.

### Day 10: Sub-phase 3.2 — the ReAct loop and the LangGraph orchestration

Built the consumer of the 3.1 tool layer: four nodes (`gather_evidence` → `reason` → `decide` → `finalize`) with exactly **one** conditional edge and **one** model call per cycle. Only `reason` talks to Claude; `gather_evidence` is an executor rather than a decider, and `decide` is a pure function of state. The first iteration is a **deterministic four-call opening sweep** — traffic, latency, errors across all three services, deploys — chosen by code rather than by the model. The trade-off is real: step one shows no visible tool-selection reasoning. What it buys is that every investigation starts from an identical evidence baseline (which is what makes the Phase 5 eval comparable), the sweep costs zero tokens, and the scripted timeout scenario finishes in **two** model calls instead of four. The `memory` fault is the case that justifies the loop existing at all — the sweep finds nothing in logs and flat metrics, so the model has to go after `downstream_memory_bytes` on turn two.

**The confidence score is not the number the model wrote down.** The model is required to call a synthetic `update_hypothesis` tool on every turn, which turns confidence into a *trajectory* (0.35 → 0.72 → 0.91) and makes "requested no read tools" an unambiguous *I am done* signal — so `decide` stays a threshold check with no prose to interpret. Then `decide` earns the number back: every citation must match the literal `query` string some tool actually issued, and a claim that does not resolve caps confidence at 0.6 regardless of what was reported. Writing that test exposed a bypass the plan had not specified — validating *each* citation means a hypothesis with **zero** citations passes vacuously, which is a cheaper route to 0.91 than citing badly, so citing nothing is capped too. `confident` additionally requires two *distinct* tools to have returned `ok=True`, because one signal is a symptom and not a diagnosis. The control tool deliberately does **not** live in `TOOLS`: that registry means "the read-only investigation surface", it is what `probe.py` offers and what the drift alarm guards, so the graph owns its own control tool and merges it into the tool list it sends.

Two API constraints shaped the design more than any of our own preferences. First, **every `tool_use` block must be answered by a `tool_result`** — and since the model's assistant turn is replayed verbatim on the next request, a call the executor declines (a duplicate, or one over the three-per-turn cap) cannot simply be dropped; it needs a synthetic result saying why it was not run. So the invariant became *every requested call produces exactly one evidence entry*, which turned out to be a better contract than the "drop and note it" the plan described: the model reads "you already asked this" instead of silently getting nothing. Second, **extended thinking requires the latest assistant turn's `thinking` blocks to come back unmodified**, signature included. That killed the tidy idea that the message list could be a pure function of the evidence, and added an `assistant_turns` field holding raw content blocks; earlier turns have their thinking stripped, since they no longer need it and it is pure tokens. Messages are otherwise rebuilt from state each turn so older evidence can collapse to its summary line — free, because the cache breakpoint sits on the last tool definition and the messages were never in the cached prefix anyway.

Model-level facts worth not rediscovering: `budget_tokens` is a **400** on Opus 5, thinking is on by default and is never disabled here (with it off the model can write a tool call into *visible text*, where the turn succeeds and the call silently never runs), `effort` lives inside `output_config`, and `display: "summarized"` costs nothing extra while putting the model's reasoning into the audit trail. `anthropic` 1.x is built on `httpx2`, which installs alongside the `httpx` 0.28 the tools use rather than fighting it. We deliberately did **not** enable server-side refusal fallbacks despite the standing recommendation for Opus 5 — they require moving the core loop to the beta endpoint, and `decide` already routes a refusal to a real report. Two bugs came only from writing the tests: a refusal has no `update_hypothesis` block, so it fell into the missing-hypothesis retry path and paid for a second call before being classified as a failure; and because `decide` and `finalize` measure elapsed time against `started_at`, a state seeded from a frozen test clock but judged by the real one reports an elapsed time of years and trips the wall-clock cap on the first cycle — so `build_graph` threads one clock through both. Finally, the graph **does not touch Postgres**: `finalize` returns a pure report and the caller persists it, which is what lets all 278 new tests run with no API key, no Docker, and no database. None of this has been run against the live stack yet; that rehearsal is the next session's first job, and until it passes the loop is unproven.

### Day 11: Moving the model call onto Bedrock

The agent now talks to **Claude Sonnet 4.5 on Amazon Bedrock** (`eu-north-1`, bearer-token auth) rather than to the first-party API. Because `agent/graph/llm.py` was built as the single seam where the agent talks to a model, the provider swap is two lines of constructor and a pricing table entry — the injectable-client design paid for itself the first time it was tested. There is no new dependency (`anthropic==1.0.0` already exports `AsyncAnthropicBedrock`) and, notably, **no boto3**: the SDK sets `Authorization: Bearer …` and returns before it ever imports the SigV4 path, and passing `aws_region` explicitly keeps its region inference — the other boto3 touch point — out of the picture too. Prompt caching survives because `llm.py` uses one *explicit* `cache_control` breakpoint; it is top-level auto-caching that the legacy Bedrock integration rejects with a 400.

What did not survive is the thinking configuration, and that is the real cost of the move. Sonnet 4.5 is a previous-generation model: adaptive thinking is 4.6+ only, and `output_config={"effort": …}` is an outright **400** there. So `thinking` went back to the explicit `{"type": "enabled", "budget_tokens": 4000}` (≥1024, and strictly under `max_tokens`), and `output_config` is not sent at all. Thinking itself stays on for the reason Day 10 recorded — with it off the model can write a tool call into visible text, where the turn succeeds and the call silently never runs. `AGENT_EFFORT` was **deleted** from `agent/config.py` rather than left in place: a knob whose only reader has stopped reading it is a trap for the next person. Three tests that asserted the old contract were inverted, which is the intended visible consequence of a contract change rather than collateral damage.

One non-obvious detail worth pinning: `estimate_cost` keys off the **literal** model string that gets sent, so the Bedrock ids needed their own `PRICING` entries. Without them every call would fall through to `DEFAULT_PRICING` (Opus rates) and overstate spend by roughly 1.7x — which trips `COST_CAP_USD` early and would quietly corrupt the Phase 5 cost baseline. The failure mode is silent, so it now has a test. Two things remain unverified until the live rehearsal, which is still the 3.2 gate and now proves both changes at once: the `eu.` cross-region inference profile id (a 404 is answered with an `AGENT_MODEL` override, not a code change), and whether Bedrock honours the cache breakpoint — `cache_read_tokens` staying at zero across a whole run would mean it does not.

### Day 12: The live rehearsal — the 3.2 gate, run against a restored deploy ledger

The loop made its first real API calls. **Three of the four faults passed cleanly; `timeout` did not**, so the gate is not closed and `CLAUDE.md` still reads 3.2. Both Day 11 unknowns are now answered: the `eu.` cross-region inference profile id resolves (no 404, no `AGENT_MODEL` override needed), and **Bedrock does honour the explicit `cache_control` breakpoint** — every call after the first in a run read exactly 2511 cached tokens, the size of the tool block. Cost landed at Sonnet rates, not the ~1.7x Opus fallthrough: a single-call run billed $0.0483 against a naive $0.0389, and the gap is precisely the 1.25x cache *write* on that same 2511-token prefix. Four investigations cost $0.44 total.

**The rehearsal had to be preceded by a ledger repair, and that turned out to be the load-bearing part.** The ledger held 7 rows, all three weeks old, and `query_deploy_history` clamps `lookback_minutes` to 1440 — so the agent could not see a single deploy and got "no code change" for free rather than earning it. Reseeding had to respect a constant the naive recipe ignores: `SWEEP_DEPLOYS_MINUTES` is **120**, so `seed_deploys.py`'s default `--hours 6` would have put most noise outside the window the agent actually reads. Seeded `--noise 6 --hours 2` instead. The payoff was immediate and is the whole argument for noise: on both no-deploy faults the agent had six candidate deploys in view and blamed none of them, rejecting the nearest on timing ("v3.7.1 deployed at 11:13, memory jumped at 11:33 — 19 min gap"), and on `bad_config` it picked the *correlated* row out of that noise and named it in the diagnosis.

**Citation integrity held perfectly — 15 citations across four runs, all resolving to a query some tool actually issued, zero dangling.** That is the mechanism Day 10 built `decide` around, and it survived contact with a real model. `memory`, the fault that justifies the loop existing, behaved exactly as designed: the sweep found nothing, the model earned two more turns, went after `downstream_memory_bytes`, and correctly read the shape as "jumped to 10MB and plateaued, not growing" rather than as a leak. `bad_config` also reproduced the Phase 1 tech debt live — data-service emitted 500s at 4.97/s while api-gateway recorded **zero** 500s, the uncaught `HTTPStatusError` bypassing the metrics middleware exactly as the captured fixtures predicted.

**The `timeout` miss is a real finding and is deferred to its own TDD cycle.** The agent got `fault_type` right but named `data-service` where ground truth says `api-gateway`, because api-gateway logs `"upstream timeout calling data-service"` and it took that string at face value — *despite* having gathered contrary evidence in the same run (data-service p99 falling to 44ms, no data-service errors, `config_errors_total` flat). It hedged honestly at 0.75 and escalated rather than claiming certainty, which is the designed behaviour, but the loop did not use evidence it already had to override a log message's implied blame. Whether that is systematic or a one-off is unknown from a single run. A second, quieter finding from `latency`: the agent identified the correlated deploy but ruled it out by comparing it against a symptom onset of 11:05 that it appears to have inferred rather than observed — the deploy actually preceded the fault by 67 seconds. Both point at the same soft spot, which is that the model's sense of *when* things happened is weaker than its reading of *what* happened, and the known `reference_time` anchoring limitation sits directly underneath it.

Two mechanical notes for whoever runs this next. `InvestigationReport` does **not** carry `cache_read_tokens` — it lives in graph state and in each `StepRecord`, so the `--json` CLI cannot answer the cache question at all; it was answered by wrapping the injected `call` collaborator in a scratchpad driver, which is exactly the seam the graph already exposes for tests, so no production code moved. And back-to-back fault runs bleed into each other through the sweep's 30m now-anchored metric window; `docker compose restart prometheus` between runs is a clean reset precisely because the TSDB is ephemeral, turning a known weakness into a convenience.

### Day 13: Write tools, the policy gate, and what a live rehearsal is actually for

Sub-phase 3.3 is built and its live gate is closed: the agent diagnosed a real `bad_config` fault, proposed `toggle_config`, the deterministic gate approved it, and the action cleared the fault — confirmed in Prometheus, where `config_errors_total` goes flat about a minute *before* the injector's own revert was due, so the flattening is attributable to the agent rather than to the fault expiring. That distinction is the whole point of insisting on independent verification: an action that reports success while the injector quietly reverts underneath it would look identical in the report.

**The architecture is "model proposes, policy disposes", and the separation is structural rather than conventional.** The three write actions live in their own `ACTIONS` registry, never in `TOOLS`, so the model is handed the read-only investigation surface and cannot call an action at all; it proposes one by name in `update_hypothesis`, and a pure function in `agent/policy/` approves or denies. A new `act` node sits between `decide` and `finalize` on the stop path, which is what makes "one action per investigation" a property of the graph's shape rather than a counter someone has to remember to check. Two tables govern the decision, and two are needed rather than one: because every fault in this stack lives in process memory, a restart or a fault-clear would incidentally fix *any* of them, so blast radius alone would make every action a universal fix and the gate a rubber stamp. `ACTION_ADDRESSES` is the independent second rule, and it is why `restart_service` is declared not to address `bad_config` even though it would clear it — blessing an action for a reason that only holds by accident is exactly the failure the table exists to prevent.

**The rehearsal earned its keep by falsifying the plan three times, and the most interesting one was a line the plan had collapsed.** The design deliberately gave the model action *names* only — a schema enum, no descriptions — on the same no-answer-key principle that governs the fault vocabulary. But the prompt asks it to "propose the narrowest action that addresses the mechanism", and that is not a judgement anyone can make from a name. Asked to remediate a configuration fault, it proposed `rollback_deploy`: entirely reasonable if you have just blamed a deploy, and always denied on blast radius. The distinction the plan missed is between an **answer key** (this fault → that action), which must never reach the model, and an action's **semantics** (what it does), which legitimately must. The `ACTIONS` descriptions — none of which names a fault type, now held by a test — are published into the `proposed_action` schema, built from the registry so they cannot drift. The next live run proposed `toggle_config` and was approved. No amount of offline testing would have surfaced this; the unit tests all passed throughout, because they test the gate's logic and the gate was never wrong.

The other two falsifications were about rule ordering. The plan listed `AGENT_ALLOW_WRITES` as gate rule #1 while also asking for a four-fault *dry* rehearsal whose verdicts match its prediction table — and those cannot both hold, since rule #1 makes every dry run report `writes_disabled` and prove nothing. The kill switch therefore belongs where it already was, in `run_action`, and the gate reaches the same verdict either way; an approved dry run reads honestly as `auto_remediate` with `executed=False, dry_run=True`. Separately, the plan predicted the `timeout` case denying on `blast_radius` when it in fact denies on `action_mismatch` first, and the ordering is right: "this would not have helped" belongs before "this is too risky", or you end up warning about the danger of something that was never the right move. `unknown_action` moved ahead of `blast_radius` for the plainer reason that you cannot look up the radius of an action that does not exist.

**Two honesty conventions were worth the effort they cost.** `ok` says whether an action did its job; `verification` says whether the world got better — so a restart that ran and left the service unhealthy is `ok=True, executed=True` with a verification saying so, because collapsing that into "failed" would make it indistinguishable from "could not restart", and those call for opposite next moves. And `action_taken` is populated only when something actually happened: a dry run, a timeout and a failed action all leave it null while `action_result` still records the attempt, because that column feeds a table of investigations and must never claim an action the system did not take. The same instinct produced the honest docstrings — `rollback_deploy` says plainly that it writes a ledger row and moves no code, and `toggle_config` says that `DELETE /admin/fault` is the runtime config surface here and that its own confirmation is self-reported.

Two methodology traps cost real runs and are worth recording because neither announces itself. A backgrounded `inject.py` killed when its shell exits never reverts the fault and never writes its ground-truth row — so the fault stays live and silently contaminates the *next* run, which then investigates a stack it was never meant to see. And `docker compose restart prometheus` between runs is necessary but not sufficient: the fault duration must also be shorter than the gap between runs. Both were found by noticing that a ground-truth row was missing, not by anything failing loudly, which is the argument for checking ground truth after every run rather than only when a result looks wrong. Finally, a transient network drop took one run down mid-rehearsal and the graph did exactly what it was built for — `status=failed`, a readable report rather than a null row, and the policy gate still consulted and recorded — which is the first time that path has been exercised by an actual failure rather than a test.

`CLAUDE.md` and `ARCHITECTURE.md` are untouched. The 3.3 plan set the condition itself: components 4, 5 and 6 flip to Complete, and Stage 3 closes, only once *both* gates are closed. 3.3's is; 3.2's `timeout` miss reproduced again today and is now the single thing standing in the way — and it matters more than it did, because the gate acts on `hypothesis.service`, so a loop that names the wrong service hands the gate the wrong target.

### Day 14: The tool was lying, and three of my own fixes lied afterwards

The `timeout` miss is **still open** — three live runs, three wrong services — but the session
changed what is known about it from "the model over-trusts a log string" to something much more
specific, and most of what was wrong turned out to be ours rather than the model's.

**The strongest refutation was arriving disguised as reassurance.** When data-service stops
receiving requests, `histogram_quantile` over empty buckets returns `NaN`; `parse_range_response`
drops those points, and `summarise` then computed a trend from the *surviving, pre-fault* points.
The committed fixture `prom_range_histogram_p99.json` is exactly this case — 18 points, the last
14 `NaN` — and it summarised as `flat at 0.00495`, when the truth is that the series went silent
seven minutes earlier. On Day 12 the model read "data-service p99 falling to 44ms", concluded
data-service was healthy, and named it anyway. **It was reasoning correctly from false evidence.**
A series whose newest surviving point lags the window end by more than `MIN_RATE_WINDOW_SECONDS`
now says so and names its last sample time. That constant is the principled threshold rather than
a new magic number: it *is* the rate window, so a wider gap means any rate over the series already
reads zero.

**The opening sweep withheld the discriminator while its own neighbour explained why it should
not.** Both `query_metrics` calls were scoped to `alert.service`; the `query_logs` call three
lines below was deliberately unscoped, commented "the cause is usually downstream of the symptom".
The metric calls contradicted their own neighbour's stated reasoning. Worth pinning permanently,
because it is a property of the victim system rather than of the agent: **api-gateway's telemetry
is byte-identical under a gateway `timeout` fault and a downstream-dep `latency` fault** — same
504s, same `upstream_timeouts_total`, same ~2s duration in the same `le=2.5` bucket, same log
line. Nothing measured at the alerting service separates them, so any diagnosis drawn only from
the alerting service is a coin flip *by construction*. The discriminators are all one and two hops
down, and the sweep now reads the whole chain.

**Three prompt rules, each general rather than an answer key.** A log line is one service's
account of what it believes happened, so naming another component is an *assertion* of blame and
not a measurement of it — which matters here because under this fault the gateway never opens a
socket to data-service at all; it sleeps, raises the timeout itself, and then logs a hardcoded
string naming a service it never contacted. The confidence rubric's top band was quietly in
tension with that, since it let a metric measured at one component corroborate a log line naming
another; both signals must now be measured **at** the component being blamed. And after the first
live run, a third: when several components go quiet at once, silence does not say which one broke
— a component that failed and one that stopped being called look identical from outside — so
follow one `trace_id`, and the hop where it stops is where the break is.

**That third rule landed, and the run that proved it is the most informative of the three.** Run 2
made the trace call and reported its result *correctly* — "the request arrived at api-gateway and
returned 504, but never reached data-service or downstream-dep" — and then blamed data-service
anyway, reading "never reached data-service" as *data-service is not responding* rather than
*api-gateway never called it*. It stopped after two iterations at 0.50 while its own diagnosis
said more was needed. Run 3 did not make the call at all, so the rule is followed inconsistently.

**The humbling part: each of the three runs was poisoned by a different evidence defect, and two
of them I introduced this session.** Adding "a series that stopped reporting outranks one that
merely moved" is right for a series that was carrying traffic and went quiet, and wrong for the
`/admin/fault` endpoints, which receive one request when a fault is set and another when it is
cleared — they are stale *by construction*, so being permanently stale they held the top slots
permanently. Run 2's entire p99 baseline was three `/admin/fault` series and the model never saw
that api-gateway's p99 was pinned at 2.485s. Coverage is the only thing that separates them:
measured on the payload, real series cover 25–35% of the window and one-shot admin endpoints
3–7%. Absolute change does not separate them, because a latency series that stops has near-zero
change by construction. Then run 3 exposed the second: `_change` compared only the first and last
points, and `rate()` series begin and end at zero around any bounded incident, so a series that
went 0 → 22 → 0 scored **0.0000** and the three slots went to `/health` and `/admin/fault` again.
`max - min` is the right reading of "change across the window" and is already computed over the
full pre-downsample point list — **identified with a failing test drafted, not yet implemented.**

**A correction to Day 12's entry, which is wrong.** It records `docker compose restart prometheus`
as "a clean reset precisely because the TSDB is ephemeral". It is not. A restart preserves the
container's writable layer; only `down`/`rm` discards it. Run 3's 30-minute window therefore
reached back far enough to swallow run 2's entire fault. `CLAUDE.md`'s ephemerality note is
accurate about `docker compose down` and has been read as licensing the weaker command.

**Two findings recorded rather than acted on.** The deploy noise is a far stronger attractor than
Day 12 suggested: both confidently-wrong runs built their causal story on a *random* seeded deploy
with a suggestive message ("refactor configuration loading", "raise worker concurrency"), reaching
0.92 and 0.85 on a service with no signal measured at it at all. And `POST /admin/fault` traffic
is visible in the agent's own metrics, which tells it precisely when a fault was injected — an
eval-integrity leak that should be closed before Phase 5 scores anything.

**What the contingency analysis now says.** The plan held a `decide` rule in reserve: cap
confidence when the blamed service has no `ok=True` signal measured at it. It is clearly indicated
— all three runs blamed a service on absence plus a deploy correlation — but it **cannot close
this gate**, because it caps confidence without changing which service gets named. Run 1 would
become "downstream-dep at 0.5": honest, still failing. Closing the gate needs either a
discriminator the model will use reliably, or a victim system whose `timeout` fault is not
genuinely ambiguous with a downstream outage. `CLAUDE.md` and `ARCHITECTURE.md` remain untouched
for the third session running, which is the correct outcome of an open gate rather than an
oversight.

## Phase 4 — Audit Trail

### Day 15: LangSmith tracing and the Postgres per-investigation summary

Stage 4's gate — "there are no traces until there are runs" — was satisfied a dozen live runs ago, and the cost of not having a trail had already been paid: Day 14's three poisoned `timeout` runs had to be diagnosed by wrapping the `call` collaborator in a throwaway driver, because nothing was recorded anywhere. **The trace id is minted by us rather than read back from langsmith.** `run_id` is a valid `RunnableConfig` key and becomes the root run's id, so a UUID created before `ainvoke` *is* the trace id — knowable in advance, writable to Postgres whatever the run then does, and needing nothing from run-tree internals. It reaches the report only when the run was actually traced, because a row that cites a trace which does not exist is worse than a null.

**Tracing is attached, not ambient, and that decision came from reading the libraries.** The obvious route — export `LANGSMITH_TRACING` and let LangChain auto-attach — fails quietly: `langsmith/utils.py`'s `get_tracer_project` is `lru_cache(maxsize=1)` over the environment and falls back to the project name `"default"`, so our configured project would have been decorative unless the variable was set before anything read it. Passing a `LangChainTracer` as a callback makes `agent/config.py` authoritative instead. The open question that created was whether the per-call spans would then be recorded at all, since langsmith's `traceable` consults the environment — and the answer, found in `langgraph/_internal/_runnable.py`, is that LangGraph searches the run manager's handlers for exactly that tracer and installs it as langsmith's parent run tree for the node's duration, so a model call inside a node is "mid-trace" by definition and nests correctly. **A related trap, confirmed against a real client:** `wrap_anthropic` patches `messages.create`, `messages.stream`, then reads `completions.create` with no `hasattr` guard, and `AsyncAnthropicBedrock` has no `completions` — so it raises `AttributeError` having already half-patched the client. A stand-in that refuses to be called lets it finish; the except path returns the half-patched-but-working client, because the wrapper mutates in place and losing an investigation to a failed wrapping is the worse trade.

**Every function in `agent/graph/trace.py` is fail-open** — the tool layer's never-raises rule applied to observability. A missing package, an unusable key or a dead network degrades to `trace_id=None` and a run that completes normally. The one deliberate exception is `traced_tool`, which guards only the wrapping: if the span machinery raises mid-call the exception travels like any other and `gather_evidence` records a crashed call, which is a truer report than a tool result invented to cover for the tracer.

**The endpoint wiring closed a listed tech-debt item, and immediately created a hazard the test suite found by falling into it.** `POST /investigate` now marks the row `running`, investigates in a `BackgroundTasks` task and writes the report back, still answering `201 pending`. But making the endpoint run the real agent meant the pre-existing endpoint tests — which post without overriding the investigator — started making live, paid model calls; the suite spent three seconds reaching for Bedrock before failing, and the `DATABASE_URL`-gated test would have done the same against the live stack. `api/tests/conftest.py` now turns `AGENT_AUTO_INVESTIGATE` off for every api test, and the tests that want a run turn it on alongside the fake that makes it safe. The row shape keeps the migration's split honest: a field gets a column only if `0001` gave it one, and everything else — fault type, citations, what was ruled out, the policy decision, the token counts — nests flat into the `evidence` jsonb so `evidence->>'fault_type'` is a query Phase 5 can write against `incidents.ground_truth_fault`.

**Nothing here has been proven live, and the docs say so.** Twelve TDD cycles, all offline; agent tests 693 → 744, api 13 → 36. ARCHITECTURE's Stage 4 rows are 🔄 rather than ✅ and `CLAUDE.md` component 8 reads "Built, live rehearsal pending" — the same standard 3.2 has been held to for three sessions. The gate is one traced run through `agent-api` reaching both LangSmith and Postgres, and it needs `LANGSMITH_TRACING`/`LANGSMITH_PROJECT` added to `docker-compose.yml` first, which are not passed today.
